지난 포스팅에서는 인덱스에 대해 좀 더 자세히 알아보며 성능 향상을 위한 인덱스 설정을 적용해보았다.

이번에는 일반적으로 발생할 수 있는 동시성 문제들에 대해 알아보고, 이를 프로젝트에 적용해보려고 한다.

이번 포스팅에는 트랜잭션, 격리 수준들에 대한 이해가 있는 것을 가정하여 작성한다.

이번 포스팅도 저번 포스팅과 마찬가지로 데중애설 7장 트랜잭션의 내용들이 포함되어 있다.

## 경쟁 조건의 다양한 예시들

### 더티 읽기
![Desktop View](/posts/p4_1.png){: .w-75 .normal}
- 한 클라이언트가 다른 클라이언트가 썼지만 아직 커밋되지 않은 데이터를 읽음
- Read Uncommitted 격리 수준에서 발생할 수 있는 동시성 문제
- TX B가 잔액을 0원으로 변경한 후 아직 커밋하지 않은 상태에 TX A가 잔액 조회 시 0원으로 조회될 수 있는 상황이다. TX B가 롤백된다면 TX A가 잔액 0원을 기반으로 어떠한 쓰기를 하면 문제가 발생할 수 있다.

### 더티 쓰기
- 한 클라이언트가 다른 클라이언트가 썼지만 아직 커밋되지 않은 데이터를 덮어씀
- Read Uncommitted 격리 수준에서 발생할 수 있는 동시성 문제

### 읽기 스큐 (비반복 읽기)
![Desktop View](/posts/p4_2.png){: .w-75 .normal}
- 클라이언트가 다른 시점에 DB의 다른 부분을 봄
- Read Committed 격리 수준에서 발생할 수 있는 동시성 문제
- TX A가 처음 조회했을 땐 계좌의 잔액이 1000원 이었는데, TX B가 그 사이에 갱신 후 커밋하였다면 TX A에서 다시 계좌를 조회할 때 그 값이 달라질 수 있다.
- 이 문제는 스냅숏 격리(Repeatable Read)를 통해 해결한다.

### 갱신 손실
![Desktop View](/posts/p4_3.png){: .w-75 .normal}
- 두 클라이언트가 조회 - 수정 - 쓰기 주기를 실행하는 경우 한 트랜잭션이 다른 트랜잭션의 변경을 포함하지 않은 채로 다른 트랜잭션이 쓴 내용을 덮어쓰면 데이터가 손실될 수 있음.
- 이는 스냅숏 격리 (Repeatable Read 격리) 수준에서 발생할 수 있는 동시성 문제
- 이자를 더하는 TX A와 수수료를 차감하는 TX B가 거의 동시에 실행되는 경우,
    - TX A는 조회 (1000원) → 수정 (1100원) - 쓰기 (1100원)
    - TX B는 조회 (1000원) → 수정 (900원) - 쓰기 (900원)
    와 같은 주기로 트랜잭션을 실행하여 운이 좋지 않게도 하나의 트랜잭션만 반영되는 경우 발생한다.
- 이 문제는 명시적 잠금을 통해 해결할 수 있다.

### 쓰기 스큐
![Desktop View](/posts/p4_4.png){: .w-75 .normal}
![Desktop View](/posts/p4_5.png){: .w-75 .normal}
- 트랜잭션이 질의를 한 결과를 기반으로 다음 쓰기를 결정하는 경우 발생할 수 있음
- 이는 스냅숏 격리 (Repeatable Read 격리) 수준에서 발생할 수 있는 동시성 문제
- 위 예시에서, 현재 당직인 의사의 수를 확인하고 이에 따라 애플리케이션 단에서 당직을 쉬는 수정 질의를 하는 트랜잭션 두 개가 동시에 실행된다면 둘 다 커밋되며 한 명도 당직을 맡게되지 않는 경우가 생길 수 있다.
- 이 또한 명시적 잠금을 사용하거나 Serializable 격리 수준에서 막을 수 있다.

### 팬텀 읽기
![Desktop View](/posts/p4_6.png){: .w-75 .normal}
- 어떠한 검색 조건에 부합하는 객체를 읽을 때, 다른 클라이언트가 그 검색 결과에 영향을 주는 쓰기를 실행하는 경우
- 이는 스냅숏 격리 (Repeatable Read 격리) 수준에서 특정 경우 발생할 수 있는 동시성 문제
- TX A가 같은 질의를 실행했음에도 처음에는 1명, 두 번째에는 2명이 반환되는 결과를 얻게된다.
- 이 또한 명시적 잠금을 사용하거나 Serializable 격리 수준에서 막을 수 있다.

### 경쟁 조건 정리
명시적 잠금 (수동 잠금) 을 통해 갱신 손실, 쓰기 스큐, 팬텀 읽기를 해결한다고 앞서 얘기했다.

mysql의 경우, 갱신 손실 방지의 경우 해당 id에 해당하는 row 자체에 잠금을 걸지만, 쓰기 스큐나 팬텀 읽기 방지의 경우 해당하는 범위에 잠금을 걸기 때문에 위 문제들을 방지할 수 있다.

- 쓰기 스큐 - on_duty = true 인 모든 row에 잠금
- 팬텀 읽기 - salary ≥ 500 인 모든 row에 잠금

Read Committed, Repeatable Read와 같은 격리 수준들은 위 경쟁 조건들의 일부는 막아주지만, 나머지는 명시적 잠금과 같은 방식으로 개발자가 수동으로 처리해줘야 한다.

직렬성 격리 만이 이 모든 문제들을 방지해준다.


## 내 프로젝트에는 어떤 동시성 문제들이 있을까?

위에서 살펴본 내용들을 토대로 내 SNS 프로젝트에 어떤 동시성 문제들이 있을지를 파악하고, 해당 경우에 어떤 방식으로 문제를 해결하는지 작성한다.

### 같은 이메일로 회원 가입 중복 실행 시
**회원 가입 코드**
``` kotlin
@Transactional
fun register(req: UserRegisterRequestDto): AuthResult {
    // 이메일 중복 체크
    if (userRepository.findByEmail(req.email) != null) {
        throw ConflictException(
            errorCode = ErrorCode.ROW_ALREADY_EXIST,
            message = "중복된 이메일 입니다.",
        )
    }

    // 비밀번호 암호화 & 유저 저장
    val user = userRepository.save(
        User(
            email = req.email,
            name = req.name,
            password = passwordEncoder.encode(req.password),
        )
    )

    // 토큰 생성
    val accessToken = jwtTokenProvider.generateAccessToken(user.id!!)
    val refreshToken = jwtTokenProvider.generateRefreshToken(user.id!!)

    // Refresh Token DB에 저장
    refreshTokenRepository.save(
        RefreshToken(
            userId = user.id!!,
            token = refreshToken,
            expiresAt = LocalDateTime.now().plusDays(7)
        )
    )

    return AuthResult(user, accessToken, refreshToken)
}
```
- 대규모 트래픽의 경우이거나, 네트워크 지연 등으로 인해 같은 이메일로 회원 가입 시도가 여러 번 실행될 수 있다.
- User의 email에 unique constraints를 구성한다면 동시에 여러 번 요청이 오더라도 하나의 요청만 성공적으로 수행될 수 있다.

**유저 엔티티에 unique constraints 설정**
``` kotlin
@Entity
@Table(
    name = "users",
    indexes = [
        Index(name = "idx_email", columnList = "email")
    ]
)
class User (
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    val id: Long? = null,

    @Column(nullable = false, unique = true)
    var email: String,

    @Column(nullable = false)
    var name: String,

    @Column(nullable = false)
    var password: String,
)
```

### 팔로우 시 발생할 수 있는 동시성 문제

해당 경우는 기존 코드에서 조금 발전된 코드에서 발생할 수 있는 동시성 문제이다.

서비스가 매우 커져 많은 유명한 인플루언서들이 사용하는 SNS 애플리케이션이라고 가정하면, 유저의 정보를 조회하는 데에 팔로잉 유저 수, 팔로워 유저 수를 count 하는 쿼리도 DB에 부담이 될 수 있다.

이를 완화하기 위해 FollowCount라는 테이블을 만들어 유저의 팔로잉, 팔로워 수를 관리하여 간단한 쿼리로 현재 유저의 정보를 조회할 수 있다.

이 과정에서 FollowCount의 값들이 User 테이블 내에 있을 수도 있지만, 그렇게 하면 User의 정보를 수정하는 요청들과 더 빈번하게 Race Condition에 놓이게 되므로 FollowCount 테이블을 따로 두었다.

자! 그렇다면 이렇게 만들기 위해 다음과 같이 코드를 수정해보자.

**팔로우 기능 코드**
``` kotlin
@Transactional
fun followUser(userId: Long, req: FollowRequestDto): Follow {
    if (req.followingId == userId) {
        throw BadRequestException(
            ErrorCode.INVALID_USAGE, "자신을 팔로우할 수 없습니다"
        )
    }

    val follower = userRepository.findByIdOrNull(userId)

    if (follower == null) {
        throw UnauthorizedException(
            ErrorCode.USER_NOT_FOUND, "유저가 존재하지 않습니다."
        )
    }

    val following = userRepository.findByIdOrNull(req.followingId)

    if (following == null) {
        throw NotFoundException(
            ErrorCode.ROW_NOT_FOUND, "유저가 존재하지 않습니다."
        )
    }

    val followerCount = followCountRepository.findByIdOrNull(userId)!!
    val followingCount = followCountRepository.findByIdOrNull(req.followingId)!!

    followerCount.followingCount += 1
    followingCount.followerCount += 1

    followCountRepository.save(followerCount)
    followCountRepository.save(followingCount)

    return followRepository.save(
        Follow(
            followerId = follower.id!!,
            followingId = following.id!!
        )
    )
}
```

이렇게 코드를 수정하면 어떤 문제가 있을 수 있을까?

매우 유명한 인플루언서는 1초 안에도 여러 명이 팔로우를 하거나 언팔로우를 하는 경우가 있을 것이다.

만약 동시에 100번 유저를 여러 명이 팔로우한다면 아래와 같은 문제가 발생할 수 있다.

![Desktop View](/posts/p4_7.png){: .w-75 .normal}

이렇게 된다면 100번 유저의 팔로워 수가 2명이 증가해야 하지만 Lost Update(갱신 손실)가 발생하여 1명만 증가하는 경우가 발생할 수 있다.

### Pessimistic Lock 적용하기
일반적으로 JPA와 같은 ORM을 사용하다보면, 위와 같은 Read → Modify → Save와 같은 패턴으로 작업을 하게된다. 이러한 경우 위에서 살펴봤던 것 처럼 Lost Update(갱신 손실)가 빈번하게 발생할 수 있으므로 이를 해결하기 위한 방법 중 하나인 Pessimistic Lock을 적용하였다.

Pessimistic Lock이란 트랜잭션 내에서 특정 row에 락을 걸어 다른 트랜잭션에서 이미 락이 걸린 row에 대한 접근을 제한하는 방식을 말한다.

Mysql에서는 트랜잭션 내에서 사용할 수 있는 2PL(Shared Lock, Exclusive Lock)을 제공하며, 이를 사용하여 Pessimistic Lock을 적용할 수 있다.

Pessimistic Lock을 적용하면 다음과 같이 동작한다.

![Desktop View](/posts/p4_8.png){: .w-75 .normal}

트랜잭션 내에서 “FOR UPDATE” 로 명시적으로 해당 row에 락을 걸어 다른 트랜잭션에서 해당 row에 접근할 수 없도록 한다.

이를 구현하면 다음과 같다.

**FollowCount 엔티티와 JPA 레포지토리**
``` kotlin
@Entity
@Table(
    name = "follow_count",
)
class FollowCount (
    @Id
    val id: Long,

    @Column(nullable = false)
    var followerCount: Long,

    @Column(nullable = false)
    var followingCount: Long,
)

interface FollowCountRepository : JpaRepository<FollowCount, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT fc FROM FollowCount fc WHERE fc.id = :id")
    fun findByIdForUpdate(id: Long): FollowCount?
}
```

**변경된 팔로우 기능 코드**
``` kotlin
@Transactional
fun followUser(userId: Long, req: FollowRequestDto): Follow {
    ... (생략)

    val followerCount = followCountRepository.findByIdForUpdate(userId)!!
    val followingCount = followCountRepository.findByIdForUpdate(req.followingId)!!

    followerCount.followingCount += 1
    followingCount.followerCount += 1

    followCountRepository.save(followerCount)
    followCountRepository.save(followingCount)

    return followRepository.save(
        Follow(
            followerId = follower.id!!,
            followingId = following.id!!
        )
    )
}
```

이렇게 하면 일반적인 경우는 문제가 없이 동작할 수 있다. 하지만 특정 상황에서 또 다른 문제가 발생한다.

동시에 User A와 B가 서로를 팔로우한다고 가정해보자.

![Desktop View](/posts/p4_9.png){: .w-75 .normal}

하나의 트랜잭션은 FollowCount A의 락을 획득하고 B의 락을 획득하기를 기다리게 되고, 다른 트랜잭션은 FollowCount B의 락을 획득하고 A의 락을 획득하기를 기다리게 된다.

이 경우 데드락이 발생하여 하나의 트랜잭션이 강제로 롤백된다.

이는 데이터 정합성에는 문제가 없을 수 있지만 유저 입장에서 ‘난 단지 팔로우만 했을 뿐인데 에러가 발생한다고?’ 하는 생각이 들 수 있다.

따라서 이를 해결하기 위해선 항상 일정한 순서로 락을 획득해야 한다.

아래 코드에서는 userId의 오름차순 순서로 FollowCount의 락을 획득하도록 수정했다.

**최종 변경된 팔로우 기능 코드**
``` kotlin
@Transactional
fun followUser(userId: Long, req: FollowRequestDto): Follow {
    ... (생략)

    val (firstId, secondId) = if (userId < req.followingId) {
        userId to req.followingId
    } else {
        req.followingId to userId
    }

    val firstCount = followCountRepository.findByIdForUpdate(firstId)!!
    val secondCount = followCountRepository.findByIdForUpdate(secondId)!!

    val followerCount = if (userId == firstId) firstCount else secondCount
    val followingCount = if (req.followingId == firstId) firstCount else secondCount

    followerCount.followingCount += 1
    followingCount.followerCount += 1

    followCountRepository.save(followerCount)
    followCountRepository.save(followingCount)

    return followRepository.save(
        Follow(
            followerId = follower.id!!,
            followingId = following.id!!
        )
    )
}
```

## 추가적인 동시성 문제 해결 방법들

이 외에도 동시성 문제를 해결하는 방법들이 여러가지 있다.

여기에서는 어떤 방법들이 있는지 정도만 확인하고 가보자.

### Optimistic Lock
Optimistic Lock은 Pessimistic Lock과 비롯하여 자주 사용되는 동시성 처리 방법이다.

이름에 Lock이 있지만 실제로 락을 사용하지는 않고, 테이블 내에 Version 값을 두어 트랜잭션 내에서 읽어온 버전 값이 같은 경우에만 UPDATE가 가능한 방식이다.

```
SELECT user_id, following_count, version
FROM follow_count
WHERE user_id = 100;

UPDATE follow_count
SET following_count = 11,
    version = version + 1
WHERE user_id = 100
  AND version = 0;
```

다른 트랜잭션으로 인해 version 값이 변경된 경우 UPDATE가 실패하고, 이를 감지하여 UPDATE가 실패한 경우 재시도하는 방식으로 사용한다.

Optimistic Lock의 주의해야 할 점은 너무 자주 충돌이 발생할 것 같은 곳에 사용할 경우 오히려 DB와 서버에 부하를 줄 수 있다는 점이다.

자주 충돌할 것 같은 경우에는 Optimistic Lock을 사용하기 보다는 Pessimistic Lock을 사용하는 것이 더 효율적일 수 있다.

### 원자적인 쿼리 사용하기
테이블 내의 특정 값을 증감하는 쿼리의 경우에는 Pessimistic Lock과 같이 명시적으로 Lock을 걸기보다는 UPDATE 쿼리를 통해 원자적으로 사용하는 것이 더 편할 수 있다.

Read - Modify - Save 패턴의 방식이 아니기 때문에 Lost Update가 발생하지 않는다.

하지만 이 경우에도 UPDATE 쿼리 실행 시 해당 row에 X-Lock이 걸리기 때문에 데드락에 주의해야 한다.

## 마치며
이번 포스팅에서는 발생할 수 있는 경쟁 조건들에 대해 알아보았고, 현재 진행 중인 프로젝트에서 발생할 수 있는 동시성 문제들과 이를 해결하고, 추가적으로 다른 동시성 문제들을 해결하는 방법들을 알아보았다.

DB에 직접 Unique Constraints를 걸거나 Pessimistic Lock, Optimistic Lock, 원자적인 쿼리를 사용하는 방법들로 동시성 문제들을 해결할 수 있지만 결국 DB에 동시에 여러 트랜잭션에서 락을 걸고 대기하는 것이 DB에 부하를 줄 수 있기 때문에 DB에 실제로 락을 거는 것 보다는 DB에 접근할 수 있는 티켓과 같은 분산 락을 사용하기도 한다.
또한, 이번 포스팅에서 주로 다루었던 Pessimistic Lock의 경우, 분산 DB 환경에서는 네트워크 지연과 같은 문제로 사용하기 어려울 수 있으며 이를 대체하기 위해서도 분산 락을 사용한다.

추후에는 분산 락을 적용해보는 포스팅도 할 수 있으리라 생각해본다..
